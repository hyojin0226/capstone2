# 정확도 추가 실험: 하이퍼파라미터 탐색, SNI 피처 (7단계, 2026-11-12)

- 질문: 운영 모델 A(held-out 0.746, 같은 설정의 시드 평균 0.723)를 유지한 채, 정확도를 더 올릴 방법이 남아 있는가?
- 이전 실험에서 판정 방식(model-improvements.md)과 패킷 시퀀스(model-sequence-features.md)는 확인했다. 남은 두 후보를 잰다.
  1. 하이퍼파라미터·규제·클래스 가중치
  2. SNI 피처 (TLS ClientHello의 서버 이름. 암호화되지 않은 메타데이터다)
- 도구: `src/model/eval_tuning_sni.py tune|sni`. 결과 원본: `data/model_eval/tuning_*.csv`, `sni_*.csv` (git 제외)
- 파이프라인은 바꾸지 않았다.

## 1. SNI 피처

**피처:**
- nDPI가 뽑은 `requested_server_name`의 마지막 두 레이블을 원-핫으로 넣는다(예: `mail.google.com` → `google.com`).
- 사전은 학습 폴드에서 5회 이상 나온 것만 쓴다. `has_sni` 플래그를 함께 넣는다.
- 지금 피처 49개에 더한다. 하이퍼파라미터는 지금 설정 그대로다.

**있는 비율:** clean 플로우의 32.8%, 바이트로는 4.9%다. 서버 이름은 nDPI가 TLS ClientHello·HTTP Host·DNS 등에서 읽은 경우에만 있다. UDP 미디어나 바이트가 큰 데이터 플로우에는 대부분 없다.

| 평가 | 지금 피처 | + SNI | 차이 |
|---|---|---|---|
| held-out 정확도 (학습 시드 10개) | 0.723 (0.719–0.729) | **0.772** (0.769–0.777) | **+0.049** |
| held-out macro-F1 | 0.634 | **0.765** | **+0.131** |
| held-out 확신도 ≥ 0.8: 답한 비율 / 정확도 | 75.6% / 0.827 | 78.6% / 0.852 | +3.0%p / +0.025 |
| 학습 세션 CV 정확도 (분할 시드 3개) | 0.547 | 0.558 | +0.011 |
| **앱 단위 제외** (처음 보는 앱, 플로우 가중) | 0.417 | 0.422 | **+0.005** |
| 앱 단위 제외 (앱 평균) | 0.508 | 0.508 | 0 |

**앱 단위 제외 (leave-one-app-out)**
- 방법: (클래스, 앱) 하나를 통째로 학습에서 뺀 뒤 그 앱을 맞히는지 본다.
- email은 앱이 하나뿐이라 뺐다.

| 클래스 / 뺀 앱 | 플로우 | 지금 피처 | + SNI |
|---|---|---|---|
| chat / gmail | 115 | 0.617 | **0.461** |
| voip / hangouts | 498 | 0.382 | **0.526** |
| streaming / vimeo | 277 | 0.715 | 0.762 |
| chat / hangouts | 92 | 0.641 | 0.696 |
| chat / skype | 165 | 0.103 | 0.073 |
| file_transfer / skype | 503 | 0.010 | 0.006 |
| voip / skype | 785 | 0.111 | 0.094 |
| 나머지 11개 | | 같거나 ±0.04 | |

해석:
- **held-out에서는 크게 오른다(+0.05, macro-F1 +0.13).** held-out 세션은 학습에 있는 앱의 다른 세션이다. 그래서 "이 서버 이름은 이 앱"을 그대로 쓸 수 있다.
- **처음 보는 앱에서는 오르지 않는다(+0.005).** SNI가 주는 것은 "서비스 유형"이 아니라 "아는 앱인지"다.
  - 예: gmail 채팅을 빼면 `google.com` 계열 이름이 email(gmail)로 끌려가 0.617 → 0.461로 떨어졌다.
  - 반대로 hangouts 음성통화는 같은 이름을 쓰는 hangouts 채팅이 학습에 남아 있어 올랐다. 둘 다 이름과 클래스의 우연한 대응이다.
- 패킷 시퀀스 실험과 같은 구조다. 정보가 많은 피처일수록 "본 것"에 대한 점수는 오르고 "처음 보는 것"에는 효과가 없다.
- 별도 발견: **지금 피처로도 처음 보는 앱의 정확도는 0.42다.**
  - skype는 chat·file_transfer·voip 세 클래스에 다 있다. 하나를 빼면 나머지 클래스로 분류되어 0.01–0.11이 된다.
  - 이 데이터로 배운 모델은 "서비스 유형의 일반 법칙"보다 "아는 앱의 패턴"에 기대고 있다. 데이터의 앱 다양성(클래스당 1–6개)이 상한을 정한다는 결론(model-sequence-features.md ③)을 다른 방향에서 확인한 것이다.

**결정: 운영 파이프라인에는 넣지 않는다.** 이유:
1. 이득이 "아는 앱"에 한정된다. 운영 환경에서 새 앱·새 도메인이 나오면 사라진다.
2. 서버 이름은 점점 보이지 않게 된다. TLS 1.3 ECH(Encrypted ClientHello)가 쓰이면 SNI가 암호화된다. 이 프로젝트의 전제는 "내용과 식별자 없이 통계로 분류"다(IP·포트를 뺀 것과 같은 이유).
3. 바이트의 5%에만 있다. 트래픽 양 기준 대시보드에는 영향이 거의 없다.

- 다만 "앱 목록이 고정된 환경(예: 사내망)"이라면 쓸 만한 선택지다. held-out +0.05는 그 환경의 기대치로 기록한다.

## 2. 하이퍼파라미터·규제·클래스 가중치

**격자 (96개):**
- 트리 깊이 3·4·6·8, `min_child_weight` 1·5·20, (트리 수, 학습률) (300, 0.1)·(800, 0.03), L2 규제 1·10, 클래스 균형 가중치 켬·끔
- subsample·colsample 0.9는 고정이다.

**고르는 방법:**
- **held-out 세션은 고를 때 쓰지 않았다.** 학습 세션(4,258행)만으로 세션 단위 5-fold CV를 했다.
- 1차는 분할 시드 1개로 96개 전부, 2차는 상위 9개와 지금 설정을 다른 분할 시드 3개로 다시 쟀다.
- held-out은 마지막에 한 번 보고만 했다. 평가 세트를 보고 고르면 그 점수는 처음 보는 데이터의 값이 아니다(confidence-threshold.md 3절과 같은 원칙).

**2차 결과 (학습 세션 CV, 분할 시드 3개 평균):**

| 설정 | 정확도 | macro-F1 | 확신도 ≥ 0.8 답한 비율 / 정확도 |
|---|---|---|---|
| **고른 설정:** 깊이 8, 300트리, 균형 가중치 끔 | **0.574** | 0.444 | 67.3% / 0.649 |
| 깊이 4, 300트리, 끔 | 0.573 | 0.440 | 51.8% / 0.737 |
| 깊이 3, 800트리, 끔 | 0.571 | 0.431 | 37.7% / 0.802 |
| 상위 9개 범위 | 0.566–0.574 | 0.428–0.444 | |
| **지금 설정:** 깊이 6, 300트리, 균형 가중치 켬 | 0.550 | 0.441 | 59.0% / 0.672 |

- 상위 9개가 **모두 "균형 가중치 끔"**이다. 깊이·규제·트리 수에 따른 차이는 0.01 안쪽이다.
- 즉 정확도가 오른 원인은 모델 구조가 아니라 **클래스 가중치**다.
  - 가중치를 끄면 많은 클래스(voip, streaming) 쪽으로 기운다. 그래서 플로우 정확도는 오르지만 macro-F1은 그대로다.
  - 클래스 균형을 맞추는 가중치는 적은 클래스(email, chat)를 놓치지 않으려고 넣은 것이다(step5-baseline).

**held-out 보고 (학습 시드 10개):**

| | 정확도 | macro-F1 | 확신도 ≥ 0.8: 답한 비율 | 답한 것의 정확도 |
|---|---|---|---|---|
| 지금 설정 (시드 평균) | 0.723 (0.719–0.729) | 0.634 | 75.6% | **0.827** |
| 고른 설정 | **0.736** (0.732–0.739) | 0.634 | 80.4% | 0.809 |
| (참고) 운영 모델 A | 0.746 | 0.701 | 75.0% | 0.839 |

- 전부 답할 때의 정확도는 +0.013 올랐다. 시드 범위가 겹치지 않으므로 우연은 아니다.
- 하지만 **운영 지점(임계값 0.8)에서는 더 낫지 않다.** 더 많이 답하지만, 답한 것의 정확도는 0.827에서 0.809로 내려간다. macro-F1도 같다.
- 운영 모델 A(0.746, 답한 것 0.839)는 고른 설정의 시드 평균보다도 위에 있다.

## 3. 결론

| 방법 | held-out | 처음 보는 앱 | 판단 |
|---|---|---|---|
| 하이퍼파라미터·규제 | +0.013 (가중치를 끈 효과. macro-F1 그대로, 임계값 0.8에서 답한 것의 정확도는 −0.018) | – | 바꾸지 않는다 |
| SNI 피처 | +0.049 (macro-F1 +0.13) | +0.005 | 넣지 않는다 (아는 앱에만 통함, ECH로 사라짐) |
| (이전) 패킷 시퀀스 | −0.006 (macro-F1 −0.05) | – | 넣지 않는다 |
| (이전) 확신도 임계값 | 답한 것 0.746 → 0.839 | – | **적용함** (ADR 0008) |

- **운영 모델 A와 지금 피처·설정을 유지한다.** 모델 쪽에서 더 시도할 수 있는 것은 거의 다 쟀다.
- 지금 데이터에서 "처음 보는 세션·앱"의 정확도를 올리는 것은 모델이 아니라 **데이터의 세션·앱 다양성**이다.
  - 클래스당 앱 1–6개, email은 앱 1개·세션 2개다.
  - 이번 앱 단위 제외 평가(지금 피처로 처음 보는 앱 0.42)가 그 근거를 하나 더한다.
- 발표에서 할 말:
  1. "정확도를 올리는 시도를 네 가지 했고, 각각 왜 오르거나 안 오르는지 **누수 없는 평가로** 쟀다."
  2. "held-out을 올리는 방법(SNI +0.05)은 찾았지만, 처음 보는 앱에서는 효과가 없어서 넣지 않았다."
  3. "대신 모를 때 모른다고 하게 해서(임계값), 답한 것의 84%가 맞는다."
