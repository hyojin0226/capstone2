# ADR 0006: 부하 테스트, 병목 분석, 튜닝 계획 (5단계)

- 날짜: 2026-11-04
- 상태: **채택** (2026-11-04 승인). replay `--rate`/`--duration`과 측정 스크립트를 구현한다. 구조를 바꾸는 튜닝(H3, H5)과 WSL 메모리 상향은 측정 결과를 보고 다시 묻는다.
- 범위: CLAUDE.md 5단계 "부하 단계별 테스트, 병목 분석, 튜닝 전후 비교"
- 관련: ADR 0002(지연 측정 범위), ADR 0003(품질·추론), ADR 0004(집계 조회 비용), ADR 0005(보존·재처리)

## 목표

CLAUDE.md의 핵심 성과 지표 가운데 **처리량**과 **E2E latency**를 부하 단계별로 측정한다.
그다음 병목을 찾아, 한 번에 하나씩 바꾸며 튜닝 전후를 같은 조건으로 비교한다.
부하를 올린 상태에서도 **데이터 신뢰성**(회계 불변식, 중복 수렴)이 유지되는지 함께 확인한다.

## 지금까지 측정한 사실 (2–4단계)

| 사실 | 값 | 출처 |
|---|---|---|
| 적재 쿼리 설정 | 트리거 5초, `maxOffsetsPerTrigger` 50,000 → **처리 상한 초당 10,000건** | compose |
| 5만 행 배치 처리 시간 | 4.2–4.5초 (prepare 약 1.6 + write 약 1.0 + 추론·지표) | step3 10절, step4 |
| E2E (100배속, 평균 약 6,200 msg/s, 시작 몰림) | p50 6.2 s, p99 12.0 s | step3 10절 |
| replay 한 프로세스 송신 상한 | 약 39,000 msg/s (JSON 생성이 한계로 추정) | step2 4절 |
| Kafka 파티션 | 3개 (Spark task 병렬도도 3) | topic describe |
| 자원 (보존 쿼리 포함 직후) | spark 4.0 / 5 GiB, seaweedfs 441–454 / 512 MiB, kafka 1.8 / 2 GiB, clickhouse 0.5 / 3 GiB | step4 6절 |
| 머신 | CPU 12, WSL VM 메모리 15 GB (`.wslconfig` 없음) | `nproc`, `free` |
| 재처리 처리량 | 6만 행 배치에 12–25초 (보존본 전체를 배치마다 다시 스캔) | step4 7·9절 |

**지금 replay로는 일정한 부하를 만들 수 없다.** 타임라인 재생은 시작 직후에 몰린다 (첫 60초에 9,912건). 배속을 올려도 부하가 고르지 않다.
그리고 데이터가 364,054건뿐이라, 초당 1만 건이면 36초면 끝난다.

## 결정 1. 부하를 만드는 방법

| 대안 | 판단 |
|---|---|
| A. 지금처럼 `--speed`로 타임라인 재생 | 부하가 고르지 않아 "초당 N건에서의 지연"을 정의할 수 없다. 부하 테스트에는 쓰지 않는다 |
| **B. `--rate N` 일정 속도 모드 추가 (채택 제안)** | 타임라인을 무시하고 초당 N건을 고르게 보낸다. 데이터가 끝나면 `--run-id-in-hash`로 새 flow_id를 만들어 반복한다. 원하는 시간만큼 일정한 부하를 유지한다 |
| C. 외부 부하 도구 (kafka-producer-perf-test 등) | 메시지 내용이 실제 스키마가 아니다. 파싱·품질·추론 비용을 재지 못한다 |

- `event_time_ms`는 송신 시각으로 둔다 (타임라인 offset 대신). 일정 부하 모드에서는 이벤트 시간 의미가 중요하지 않다. 지연은 `replay_sent_ms` 기준이다.
- 39,000 msg/s를 넘는 부하가 필요하면 producer를 여러 개 띄운다 (`--rate`를 나눠서).
- **승인 필요:** producer에 `--rate`와 `--duration` 옵션 추가.

## 결정 2. 무엇을, 어떻게 재는가

| 지표 | 정의 | 출처 |
|---|---|---|
| 처리량 (유지 가능) | 단계별 목표 부하에서 **Spark가 뒤처지지 않는 최대 부하**. 판정: 정상 구간(예: 3분) 동안 Kafka 끝 offset − 처리된 끝 offset(lag)이 늘지 않고, 배치 처리 시간이 트리거보다 짧다 | Kafka offsets, `pipeline_batches.end_offsets`, `batch_seconds` |
| E2E latency | `inserted_at − replay_sent_ms`의 p50 / p95 / p99. 정상 구간의 행만 센다 (워밍업 제외). 측정 범위는 ADR 0002대로 수집기 출력 이후 구간이다 | `flows_raw` |
| 단계별 시간 분해 | 송신 → Kafka (`kafka_timestamp_ms − replay_sent_ms`), Kafka → 처리 (`spark_processed_ms − kafka_timestamp_ms`), 처리 → 적재 (`inserted_at − spark_processed_ms`) | `flows_raw` |
| 배치 내부 | prepare / write / 전체 시간, 배치 크기 | `pipeline_batches` |
| 자원 | 컨테이너별 CPU %, 메모리 (5초 간격 샘플) | `docker stats` |
| ClickHouse 부담 | 활성 part 수, merge 수 | `system.parts`, `system.part_log` |
| 신뢰성 | 회계 불변식(보낸 수 = 저장 + reject), FINAL 중복 0 | `verify_step3.py`의 회계·중복 항목 |

- **측정 스크립트 (제안):** `infra/scripts/load_test.sh <rate> <duration>`
  1. 초기화하고 부하를 보낸다.
  2. 실행하는 동안 자원·lag를 5초마다 CSV로 남긴다.
  3. 끝나면 위 지표를 한 줄 요약으로 출력한다.
  - 결과 CSV는 `data/loadtest/`에 둔다 (git 제외). 요약 표는 docs에 남긴다. 새 라이브러리는 쓰지 않는다 (matplotlib는 이미 있다).

## 결정 3. 부하 단계

| 단계 | 목표 부하 (msg/s) | 정상 구간 | 비고 |
|---|---|---|---|
| L1 | 500 | 3분 | 1배속 평균(62)보다 충분히 높은 기준 부하 |
| L2 | 2,000 | 3분 | |
| L3 | 5,000 | 3분 | |
| L4 | 8,000 | 3분 | 지금 상한(10,000)에 가깝다 |
| L5 | 10,000 / 12,000 | 3분 | 상한 확인. 뒤처지는 지점을 찾는다 |
| L6+ | 튜닝 후 단계를 올려 다시 찾는다 | | 39,000을 넘으면 producer 2개 |

- 단계마다 앞에 워밍업 1분을 둔다 (Python worker 시작, 모델 로딩). 이 구간은 지표에서 뺀다.
- 같은 단계를 2번 재서 편차를 본다. 편차가 크면 3번 잰다.
- 오류 주입은 끈다. 정상 데이터 처리량을 잰다. 신뢰성 확인용으로 한 단계에서만 `--inject-faults 0.01`을 켠다.

## 결정 4. 병목 가설과 튜닝 후보

**원칙:** 한 번에 하나만 바꾼다. 바꾸기 전과 후를 같은 부하 단계(병목이 드러난 단계)에서 잰다. 결과는 표로 남긴다.

| # | 가설 | 근거 | 튜닝 후보 | 볼 지표 |
|---|---|---|---|---|
| H1 | **처리량 상한은 설정값이다** (50,000 / 5초 = 10,000/s) | 설정 그 자체 | `maxOffsetsPerTrigger`를 올리거나 없앤다 (배치 크기 상한은 메모리로 정한다) | 유지 가능 처리량 |
| H2 | **E2E 지연의 대부분은 트리거 대기다** | p50 6.2초 중 배치 처리는 약 2초 | 트리거 5 → 2 → 1초 | E2E p50/p95, ClickHouse part 수 (insert가 잦아지는 대가) |
| H3 | **prepare 단계가 무겁다**: 원문(`raw_value`, 행당 약 2 KB)을 포함한 배치를 persist하고, 집계를 여러 번 한다 | prepare 약 1.6초, Spark 메모리 4.0 / 5 GiB | `raw_value`를 reject 행에만 남기고 persist에서 뺀다, 개수 집계를 한 번에 | prepare 시간, Spark 메모리 |
| H4 | **JDBC 쓰기 병렬도가 3이다** (Kafka 파티션 = task 수) | 파티션 3개, CPU 12개 | 쓰기 전 repartition(6–12), `batchsize` 조정 | write 시간 |
| H5 | **Kafka 파티션 수가 병렬도를 제한한다** | 파티션 3개 | 파티션 3 → 6 (토픽 재생성 필요. flow_id → 파티션 매핑이 바뀐다) | 처리량, CPU 사용률 |
| H6 | 보존 쿼리가 같은 JVM에서 자원을 나눠 쓴다 | 1분마다 대량 쓰기 | 보존 트리거 조정, 영향을 따로 측정 (보존 쿼리를 켜고 끈 비교) | 처리량 차이 |
| H7 | 추론은 병목이 아니다 (대상이 2.4%) | 안정 구간 추론 비용은 지연에 거의 드러나지 않았다 (step3 5절) | 확인만. 필요하면 시작할 때 모델 warm-up | 배치 1 지연 |
| H8 | 메모리가 먼저 한계에 닿는다 | spark 4.0/5, seaweedfs 0.45/0.5, kafka 1.8/2 GiB | 컨테이너 한도 재배분. WSL 메모리 상향(`.wslconfig`, 사용자 작업) | OOM 여부, 자원 CSV |

**재처리 처리량 (별도 실험):** 지금 재처리 잡은 배치마다 보존본 전체를 다시 스캔한다.
후보는 "한 번만 읽고 offset 범위로 repartition"과 "dt/hr 파티션 단위 처리"다. 36만 건 재처리 시간으로 전후를 비교한다 (지금 98–116초).

**ADR 0004 집계 조회 비용:** 집계 뷰(B1)는 6단계에서 만든다. 그래서 5단계에서는 `flows_raw FINAL` 위의 1분 윈도우 GROUP BY 쿼리를 대신 쓴다.
행 수를 늘려 가며(36만 → 수백만) 조회 시간 p95를 재고, refreshable MV(B4)로 바꿀지 판단 근거로 남긴다.

## 결정 5. 자원 한도와 안전장치

- 지금 배분: kafka 2 + clickhouse 3 + spark 5 + seaweedfs 0.5 = 10.5 GB. WSL VM은 15 GB다.
- 부하 테스트 중에는 Spark 배치 컨테이너(재처리, 3 GB)를 동시에 돌리지 않는다.
- **WSL 메모리 상향(호스트 32 GB → `.wslconfig` `memory=24GB`)은 사용자 작업이다.** H8에서 메모리가 병목으로 확인되면 그때 요청한다. 지금은 바꾸지 않는다.
- WSL이 배포판을 종료하는 문제(step4 5-2)를 막기 위해, 부하 테스트 동안 `wsl.exe -d Ubuntu -- sleep infinity`를 유지한다.
- 부하 테스트는 `--run-id-in-hash`로 flow_id를 새로 만든다. 그래서 `flows_raw`가 커진다 (수백만 행). 테스트가 끝나면 `reset_pipeline.sh`로 정리한다.

## 산출물과 완료 기준

| 산출물 | 내용 |
|---|---|
| `docs/step5-load.md` | 단계별 결과 표, 병목 분석, 튜닝 전후 비교 표, 그래프(처리량–지연 곡선) |
| 튜닝 결정 | 채택한 설정 변경과 근거. compose와 코드에 반영 |

**완료 기준**
1. **튜닝 전 기준선:** L1–L5의 처리량, E2E p50/p95/p99, 자원을 기록한다 (각 2회).
2. **병목 근거:** 가설 H1–H8 각각을 측정으로 확인하거나 기각한다.
3. **튜닝 전후 비교:** 최소 3개 변경을, 같은 단계에서 전후 수치로 비교한다.
4. **신뢰성:** 최종 설정의 최고 유지 부하에서 오류 주입 1%를 켜고 `verify_step3`의 회계·중복·추론 대상 항목이 통과한다.
   장애 테스트(`failure_test.sh`)를 그 부하에서 한 번 다시 돌려 FINAL로 수렴하는지 본다.

**목표치에 대해:** 지금은 숫자 목표를 정하지 않는다. 기준선을 재고 나서 정한다. 기준선 없이 정한 목표는 근거가 없다.
대신 지금 확인할 수 있는 예상은 이렇다. 튜닝 전 유지 가능 처리량은 설정 상한인 **초당 10,000건 안팎**일 것이고, E2E p50은 트리거(5초)의 영향으로 **5초 안팎**일 것이다.

## 승인이 필요한 것

1. replay `--rate`, `--duration` 옵션 (결정 1)
2. 측정 스크립트 `load_test.sh`와 자원 샘플러 (결정 2, 새 라이브러리 없음)
3. 튜닝 후보 중 구조를 바꾸는 것
   - H5 Kafka 파티션 3 → 6: 토픽 재생성이 필요하고, 보존본·재처리 검증을 다시 해야 한다
   - H3 `raw_value` 처리 변경: 품질 검사 코드를 고친다
   - 측정 결과를 보고 다시 묻는다.
4. WSL 메모리 상향은 측정 후 필요할 때 요청한다 (사용자 작업)
