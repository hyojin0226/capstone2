# ADR 0007: 집계 뷰, Grafana 대시보드·알림, 이상 주입 검증, dbt (6단계)

- 날짜: 2026-11-10
- 상태: **채택** (2026-11-10 승인). 구현 순서: 뷰·검증 → Grafana 프로비저닝 → 패널 비용 측정 → 증폭 주입·알림·탐지 지연 → lag 패널 → dbt → 문서
- 범위: CLAUDE.md 6단계 "dbt, Grafana 대시보드, 이상 주입 알림 검증"
- 관련: ADR 0002(멱등 키, 지연 측정 범위), ADR 0004(조회 시점 집계 B1 + dbt B3), ADR 0005(S3 보존·재처리), ADR 0006·docs/step5-load.md(성능, 조회 비용 11절)
- 계획 요약: docs/status-and-plan.md 3절

## 목표

1. 파이프라인 결과(유형별 트래픽, 품질)와 상태(지연, 배치, lag)를 **실시간 대시보드**로 보인다.
2. 트래픽 급증을 **규칙 기반 알림**으로 탐지한다. 그리고 replay 중 특정 트래픽을 인위적으로 증폭 주입해 **탐지 지연**을 잰다 (CLAUDE.md 확정 결정).
3. 시간·일 단위 이력을 **dbt**로 만들고, 원천과의 합계 일치를 테스트로 보장한다 (ADR 0004 B3).
4. 이 모든 것이 중복·재처리 뒤에도 맞아야 한다. 핵심 성과인 데이터 신뢰성을 대시보드까지 이어 간다.

## 결정 3. 집계 뷰 (ADR 0004 설계 그대로 구현)

| 뷰 | 내용 |
|---|---|
| `flows_dedup` | `flows_raw FINAL`에서 오류 주입 행(`fault_type != ''`)을 뺀다. 모든 트래픽 집계의 출발점 |
| `traffic_by_class_10s` / `_1m` | `toStartOfInterval(event_time)` × 클래스(`if(inferred, pred_service_class, 'unclassified')`, 배경은 `background`) → `uniqExact(flow_id)`, 바이트, 패킷 |
| `quality_by_window` | `flows_rejected FINAL`의 사유별 수, `flows_raw FINAL`의 flag 수, 오류 주입 수 |
| `pipeline_latency_by_window` | `inserted_at` 윈도우별 E2E 분위수. 배치 시간·행 수는 `pipeline_batches`에서 |

- 규칙: Grafana와 dbt는 **뷰만 조회한다.** 테이블을 직접 조회하면 merge 전 중복이 섞인다 (ADR 0004 반대 근거 2).
- 모든 패널 쿼리에 `event_time_ms` 범위 조건을 넣는다. 지금 정렬 키에서는 granule을 건너뛰지 못하지만, 키가 바뀌는 환경(실제 수집 시각)에서는 바로 효과가 난다.
- 검증 (ADR 0004 검증 기준):
  1. 합계 일치: 모든 윈도우·클래스의 플로우 수 합 = `flows_dedup` 행 수. 바이트 합 = 원시 합. 차이 0.
  2. 중복 내성: 장애 테스트 직후(OPTIMIZE 전) 집계 = 깨끗한 실행의 집계. 모든 (윈도우, 클래스)에서 차이 0.
  3. 재추론 반영: 시나리오 ② 직후 클래스별 합계 = 새 모델 예측 분포.

## 결정 4. 조회 비용 정책: 먼저 재고, 넘으면 TTL

`flows_raw` 정렬 키를 유지했으므로(step5-load 11-3), 비용을 묶는 방법은 다음 중에서 고른다.

| 방법 | 효과 | 대가 |
|---|---|---|
| A. 아무것도 안 함 | 시연 규모(수백만–수천만 행)에서는 패널 p95 0.5–3초 | 데이터가 쌓이면 계속 느려진다 |
| **B. `flows_raw` TTL (예: `inserted_at + INTERVAL 24 HOUR`)** | 테이블 크기가 묶이므로 조회 비용도 묶인다 | 오래된 원시 행은 ClickHouse에서 사라진다. 원본은 S3 보존본에 있고(ADR 0005), 이력은 dbt 테이블에 남긴다 |
| C. refreshable MV (B4, 예: 10초마다 최근 30분 재계산) | 패널 N개가 같은 집계를 공유한다 → 조회 횟수가 N분의 1 | **지금 정렬 키에서는 갱신 한 번이 테이블 전체를 읽는다.** 비용 상한을 만들지 못한다. 단독으로는 해결책이 아니다 |
| D. 시간순 보조 테이블 (MV로 복사, `ORDER BY (구간, flow_id)`) | 최근 구간 조회가 빠르다 | 11-3에서 기각한 문제(같은 데이터 재전송 시 중복 미제거)가 대시보드 쪽에 그대로 생긴다 |

> **측정 결과 (2026-11-10, docs/step6-dashboard.md 3절):** 기준은 약 1,500만 행까지 지켜진다. 10,000/s에서 기준을 지키려면 TTL이 약 25분이어야 하고, 그러면 실행 전체를 원천과 맞추는 검증이 깨진다. **TTL 미적용 + 운영 범위 문서화로 결정 (2026-11-10 승인).** 운영 범위: 10초 새로고침 기준 flows_raw 약 1,500만 행 이하, 오탐 30분 측정은 5,000 msg/s.

**제안:**
- 대시보드를 만든 뒤 실제 패널 쿼리의 p95를 `query_cost.py`로 잰다. 기준(안)은 패널당 p95 ≤ 1초, 새로고침 10초에서 ClickHouse CPU 평균 50% 이하다.
- 넘으면 B(TTL)를 적용한다. 그래도 패널 수 때문에 넘치면 C를 B 위에 더한다.
- 그러면 "뜨거운 데이터 = `flows_raw`(TTL), 따뜻한 이력 = dbt 집계 테이블, 차가운 원본 = S3 보존본" 3층 구조가 된다.
- TTL을 쓰면 재처리 규칙을 정한다: TTL보다 오래된 구간을 재처리하면 그 행은 다음 merge에 다시 지워진다. 그래서 오래된 구간의 재처리는 "dbt 이력 재빌드용"으로 한정하고, 그 절차를 문서화한다.

## 결정 5. 알림 규칙: 닫힌 윈도우의 기준선 대비 급증

- 도구: Grafana unified alerting. 규칙도 파일로 프로비저닝한다.
- 규칙 (클래스별):
  - 평가 대상은 **닫힌 윈도우**다 (`window_end ≤ now − L`). 늦게 도착한 행이 이미 평가한 값을 바꾸지 않게 한다 (ADR 0004 반대 근거 3).
  - 급증 비율 = 마지막 닫힌 10초 윈도우의 플로우 수 / 직전 5분 윈도우 평균.
  - 비율이 K를 넘고(초기값 3) 절대량이 최소값보다 크면(작은 수의 흔들림 방지) 알린다.
  - 평가 주기 10초. pending 시간 0초(한 번만 넘어도 알림)로 시작해, 오탐을 보고 조정한다.
- 허용 지연 L: E2E p95를 덮어야 한다. 5,000 msg/s 기준 p95가 8–14초라서 **L = 15초**로 시작한다.
- 예상 탐지 지연 (주입 시작 → 알림 발생):
  - 윈도우가 닫히기까지 최대 10초 + L 15초 + 평가 주기 최대 10초 + 조회 시간
  - 대략 20–35초로 본다. ADR 0004 목표안 p95 ≤ 30초와 경계에 있다.
  - 실측 뒤 윈도우 5초, L 10초 같은 조정과 오탐의 균형을 기록한다.
- 탐지 시각 기록: Grafana 알림 상태 이력(state history)에 남는 Pending/Alerting 전이 시각을 API로 읽는다. 외부 알림 채널(메일, 슬랙)은 이번 범위가 아니다.
- 클래스는 **예측 클래스**다 (실제 운영에는 라벨이 없다). 그래서 탐지 결과에는 모델 오분류의 영향이 섞인다. 라벨 클래스 기준 값도 함께 기록해 둘을 나눈다.

## 결정 6. 이상 주입 도구: replay 증폭 구간

- `producer.py`에 옵션을 추가한다. 예: `--amplify streaming:5:120:60`은 "120초부터 60초 동안 streaming 플로우를 5배로 보낸다"는 뜻이다. 일정 속도 모드(`--rate`)와 함께 쓴다.
- 증폭분은 새 `flow_id`로 만든다 (`run_flow_id(base, run_id, 증폭 회차)`). 실제 추가 트래픽처럼 세기 위해서다.
- 증폭분의 `run_id`에 `-amp` 접미사를 붙인다. ClickHouse 스키마를 바꾸지 않고도 주입 행을 구분해 검증할 수 있다.
- 주입 시작·끝 시각(epoch ms)을 replay 로그에 남긴다.
- 측정 계획:
  - 배율 {2, 3, 5} × 반복 5회 × 배경 부하 {2,000, 10,000 msg/s} → 탐지 여부와 탐지 지연 p50·p95
  - 오탐: 주입 없는 정상 replay 30분 동안 알림 수
  - 스트레스: Spark 재시작 직후 주입했을 때의 탐지 지연 (밀린 데이터가 처리되는 동안)
- 측정 스크립트는 `infra/scripts/alert_test.sh`로 둔다: 초기화 → replay(증폭) → Grafana 상태 이력 조회 → 요약.

- **결과 (2026-11-10, docs/step6-dashboard.md 4절):**
  - 배율은 {2, 3, 5} 대신 {3, 5, 8}을 쟀다. F2 필터와 오분류 때문에 예측 비율이 라벨 비율의 약 0.7배라 ×2는 K = 3에 닿을 수 없다.
  - 탐지: ×3 0/10, ×5 9/10, ×8 10/10. 지연 p50 35.1초, p95 47.8초다.
  - 오탐: 정상 30분 동안 0건 (같은 구간의 refire 1건 별도).
  - Spark 재시작 직후 주입: 3/3 탐지, 지연 34–44초.
  - 지연이 예상 20–35초보다 긴 것은 부분 윈도우 대기 10초 때문이다. 현재 설정(10초 / L 15초 / K 3)은 유지하고 조정 후보를 기록했다.

## 결정 7. 상태 패널과 Kafka lag (새 인프라 없이)

- 배치·지연·정확도 패널은 기존 테이블·뷰로 그린다 (`pipeline_batches`, `realtime_holdout_accuracy`, 결정 3의 뷰).
- Kafka lag(Kafka 끝 오프셋 − 처리한 오프셋)는 ClickHouse에 없다.

| 대안 | 판단 |
|---|---|
| **작은 lag 기록 스크립트 (채택 제안)** | `infra/scripts/lag_reporter.py`가 5초마다 Kafka 끝 오프셋(이미 쓰는 confluent-kafka)과 `pipeline_batches.end_offsets`를 비교해 ClickHouse `pipeline_lag` 테이블에 쓴다. 새 라이브러리가 없다. 실험·시연 때 venv에서 띄운다 |
| kafka-exporter + Prometheus | 표준적인 방법이지만 서비스 2개가 늘고 메모리 예산을 쓴다. 이 프로젝트 범위에 비해 크다 |

- **결과 (2026-11-10, docs/step6-dashboard.md 5절):** 채택안대로 구현했다 (`009_pipeline_lag.sql`, `lag_reporter.py`, 패널 2개).
  - 5,000/s에서 Spark를 40초 멈추면 lag이 21.7만(예상 22.9만)까지 늘었다. 재시작 뒤 53초 만에 정상 범위로 돌아왔고, 그중 28초가 Spark 기동이다.

## 결정 8. dbt (새 도구, 승인 필요)

| 대안 | 판단 |
|---|---|
| **dbt-core + dbt-clickhouse 1.10.3 (채택 제안)** | 이력 모델, 증분 처리, 테스트, 문서를 한 도구로 한다. CLAUDE.md 계획에 있는 도구다 |
| ClickHouse SQL 스크립트 + cron | 가볍다. 하지만 테스트·의존성·문서화를 직접 만들어야 한다 |

- 설치: 파이프라인 venv와 의존성이 섞이지 않게 **별도 venv** `.venv-dbt`를 쓴다.
  - dbt-clickhouse 1.10.3(2026-09-15)은 `dbt-core>=1.9`, `dbt-adapters<1.25`를 요구한다.
  - 함께 해결되는 dbt-core 버전을 설치 때 확인하고 `dbt/requirements.txt`에 고정한다.
- 모델 (`dbt/`):
  - `stg_flows`: `flows_dedup` 뷰 위의 얇은 뷰
  - `traffic_hourly`: 시간 × 클래스 이력. incremental, 시간 단위 delete+insert
  - `quality_hourly`
  - `model_accuracy_daily`: `flow_predictions` 기반 모델별
- 테스트:
  - not_null, accepted_values(클래스)
  - **원천 합계 일치** (사용자 정의 테스트: 기간별 `traffic_hourly` 합 = `flows_dedup` 행 수)
- 재처리 뒤 절차: 해당 기간을 `dbt build --vars`로 재빌드한다. 결과가 재처리 전 결과와 같은지 확인한다 (시나리오 ①). 재추론 결과가 반영되는지도 확인한다 (시나리오 ②).

- **결과 (2026-11-10, docs/step6-dashboard.md 6절):**
  - 버전: dbt-core 1.12.6 + dbt-clickhouse 1.10.3 (`.venv-dbt`, `dbt/requirements.txt`). 결과는 `capstone_dbt`에 둔다.
  - 증분은 delete+insert 대신 `insert_overwrite`(시간 파티션 교체)로 했다. 재추론 뒤 사라진 클래스의 옛 행이 남지 않게 하려는 것이다.
  - 테스트 14개를 두었다. 시나리오 ① 뒤 재빌드 지문이 기준과 같고, 시나리오 ② 뒤 B 예측 분포가 반영되었다.

## 자원

- dbt와 lag 기록 스크립트는 venv 프로세스다 (수백 MB 이하, 상주하지 않음).

## 반대 근거 (이 제안의 약점)

1. **도구가 셋 늘어난다** (Grafana, 플러그인, dbt). 시연 환경이 무거워지고 버전 관리 대상이 는다. 모두 버전을 고정하고 프로비저닝 파일로 재현성을 확보하는 것으로 대응한다.
2. **탐지 지연 목표(30초)가 빠듯하다.** 지연의 대부분(윈도우 + L)은 정확성을 위한 대기다. 목표를 맞추려고 L을 줄이면 늦은 행 때문에 오탐·미탐이 는다. 이 균형을 측정해 그대로 기록한다.
3. **예측 클래스 기준 알림은 모델 오분류에 영향받는다.** 라벨 기준 값을 함께 기록해 파이프라인 지연과 모델 오류를 나눈다.
4. **TTL은 "ClickHouse에서 과거 원시 행을 바로 볼 수 있다"는 성질을 포기한다.** 필요할 때만, 측정 뒤에 적용한다.
5. **날짜별 환경 편차(H9c)** 때문에 탐지 지연도 실행마다 흔들릴 수 있다. 같은 세션에서 반복 측정해 분포로 보고한다.
