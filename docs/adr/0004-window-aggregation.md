# ADR 0004: 시간 윈도우 집계를 어디서 할 것인가

- 날짜: 2026-10-27
- 상태: **제안**. 승인 전에는 구현하지 않는다.
- 관련: ADR 0002 결정 5(멱등 적재), ADR 0003 결정 6(held-out 정확도), CLAUDE.md "확정된 설계 결정"
- **주의:** 이 ADR의 권장안은 CLAUDE.md의 확정 결정("Spark는 … 시간 윈도우 집계를 담당한다")을 바꾼다. 승인되면 CLAUDE.md도 함께 고친다.

## 무엇을 집계하는가

6단계 대시보드와 이상 징후 알림의 입력이다.

| 지표 | 단위 | 쓰임 |
|---|---|---|
| 서비스 유형별 플로우 수, 바이트, 패킷 | 윈도우(예: 10초, 1분) × `pred_service_class` | 유형별 트래픽 대시보드, 급증 탐지 알림 |
| 배경 트래픽 양 (`NOT f2_passed`) | 윈도우 | 배경 대비 서비스 트래픽 비율 |
| 품질 지표: reject 수(사유별), flag 수, 오류 주입 수 | 윈도우 | 데이터 품질 모니터링 |
| 파이프라인 지표: E2E 지연 분위수, 배치 처리 시간 | 윈도우(`inserted_at` 기준), 배치 | 파이프라인 상태 모니터링 |

- 트래픽 지표의 시간축은 `event_time`(재생 타임라인상 플로우 종료 시각)이다.
- 파이프라인 지표의 시간축은 `inserted_at` / `spark_processed_ms`다.
- 오류 주입 행(`fault_type != ''`)은 트래픽 지표에서 뺀다.

## 판단 기준

1. **at-least-once 중복이 집계에 미치는 영향.** 장애가 나면 배치 하나가 두 번 쓰인다 (실측 13,943–18,684행, docs/step2·step3). merge 전에는 테이블에 그대로 보인다.
2. **재처리 후 집계를 다시 맞추는 방법.** ADR 0005의 두 시나리오가 있다.
   - MinIO에서 복구: 같은 flow_id의 행이 다시 쓰인다.
   - 새 모델로 재추론: **같은 flow_id 행의 `pred_service_class`가 바뀐다.** 행이 늘어나는 것이 아니라 값이 바뀐다.
3. **Grafana 알림 지연.** 급증이 실제로 일어난 때부터 알림이 뜰 때까지의 시간.

## 대안

| 대안 | 방식 |
|---|---|
| A. Spark 워터마크 집계 | 같은 Spark 앱에 이벤트 시간 윈도우 집계 쿼리를 추가한다. 결과를 ClickHouse 집계 테이블에 upsert한다 |
| B1. ClickHouse 조회 시점 집계 (뷰) | 중복이 정리된 `flows_raw`(FINAL 또는 argMax) 위에 GROUP BY 뷰를 둔다. Grafana가 조회할 때마다 계산한다 |
| B2. ClickHouse 증분 MV (SummingMergeTree / AggregatingMergeTree) | insert될 때마다 MV가 블록 단위로 합계를 누적한다 |
| B3. dbt 모델 | 일정 주기로 `flows_raw` FINAL에서 집계 테이블을 다시 만든다 (윈도우 단위 delete+insert) |
| B4. ClickHouse refreshable MV (`REFRESH EVERY`) | 주기적으로 쿼리 전체를 다시 계산해 테이블을 교체한다 |

### 기준 1: at-least-once 중복의 영향

| 대안 | 중복이 들어오면 | 판정 |
|---|---|---|
| A. Spark 집계 | **Spark 재시작 때문에 같은 배치를 다시 실행하는 경우는 안전하다.** state store가 마지막 커밋 버전에서 복원되고, 같은 offset 범위로 같은 결과를 다시 계산하므로, (윈도우, 클래스) 키로 upsert하면 멱등이다. **하지만 같은 flow_id가 다른 배치로 다시 들어오는 경우**(replay를 다시 보냄, MinIO 복구)는 두 번 센다. 막으려면 `dropDuplicatesWithinWatermark(flow_id)`가 필요하고, 이것은 워터마크 범위 안의 중복만 막는다 | △ 조건부 |
| B1. 조회 시점 집계 | FINAL 또는 `argMax(…, spark_processed_ms)`로 flow_id당 한 행만 보고 센다. 중복이 어떤 경로로 들어와도 결과가 같다 | ○ |
| B2. 증분 MV | MV는 **merge 전의 insert 블록**을 본다. 다시 쓰인 배치를 그대로 한 번 더 더한다. 플로우 수는 `uniqExactState(flow_id)`로 막을 수 있지만, 바이트·패킷 합계(sum)는 막을 수 없다 | ✗ |
| B3. dbt | 원천을 FINAL로 읽어 다시 만든다 | ○ |
| B4. refreshable MV | 매번 전체를 다시 계산하므로 FINAL 기준이면 중복 영향이 없다 | ○ |

### 기준 2: 재처리 후 다시 맞추기

| 대안 | MinIO 복구 (같은 행을 다시 씀) | 새 모델 재추론 (예측 값이 바뀜) |
|---|---|---|
| A. Spark 집계 | 이미 닫힌 윈도우는 state에서 빠져서 갱신되지 않는다. 체크포인트를 지우고 전체를 다시 집계해야 한다 | 옛 예측으로 센 값을 빼는 방법이 없다. 전체 재집계가 필요하다 |
| B1. 조회 시점 집계 | **할 일 없음.** 다음 조회부터 맞다 | **할 일 없음.** FINAL이 version이 큰(새 모델) 행을 고른다 |
| B2. 증분 MV | 다시 쓴 만큼 더해진다 (틀림) | 새 클래스에 더하고 옛 클래스에서는 빼지 않는다 (틀림) |
| B3. dbt | 해당 기간을 다시 빌드하면 된다 | 해당 기간을 다시 빌드하면 된다 |
| B4. refreshable MV | 다음 refresh에서 맞아진다 | 다음 refresh에서 맞아진다 |

### 기준 3: Grafana 알림 지연

탐지 지연 = 플로우가 ClickHouse에 보이기까지 + 윈도우가 닫히기를 기다리는 시간 + Grafana 평가 주기 + 지속 조건(pending)

| 대안 | ClickHouse에 집계가 보이는 시점 | 비고 |
|---|---|---|
| A. Spark 집계 | append 모드: 워터마크 지연(예: 30초)만큼 더 늦다. update 모드: 매 트리거(5초)마다 부분 집계 | **원시 행보다 빠르지 않다.** 같은 foreachBatch 주기 안에서 원시 행도 ClickHouse에 들어간다 (현재 E2E p50 6.2초, p99 12.0초) |
| B1. 조회 시점 집계 | 원시 행이 적재되자마자 (p50 6.2초, p99 12.0초) | 늦게 도착한 행은 과거 윈도우 값을 바꾼다. 알림은 "닫힌 윈도우"만 평가하는 규칙으로 다룬다 (아래) |
| B3. dbt | 실행 주기(분 단위) | 알림용으로는 느리다 |
| B4. refreshable MV | refresh 주기(예: 10–30초) | B1보다 주기만큼 늦다 |

**결론: 지연은 A와 B1의 차이를 가르지 못한다.** Spark 집계도 같은 마이크로배치 주기에 묶여 있고, 결국 Grafana가 ClickHouse를 조회해야 알림이 뜨기 때문이다.
B1에 Grafana 평가 주기(예: 10초)와 닫힌 윈도우 대기(예: 10초)를 더하면, 탐지 지연은 대략 30초 안이 될 것으로 본다.
실측은 6단계 이상 주입 실험에서 한다.

## 권장: B1 (중복 제거된 `flows_raw` 위의 ClickHouse 조회 시점 집계)과 B3 (dbt, 이력·분석용)

**말씀하신 방향에 동의한다.** 판단을 가른 것은 기준 1, 2다.
- 이 파이프라인의 신뢰성 모델은 "중복은 들어올 수 있고 flow_id로 수렴한다"이다 (ADR 0002).
- 집계도 **수렴한 결과 위에서** 계산해야 이 모델과 일관된다.
- 재추론은 행의 값을 바꾸는데, 이 변화를 추가 작업 없이 반영하는 것은 B1과 B3뿐이다.

| 용도 | 방식 |
|---|---|
| 실시간 대시보드, 알림 | B1: ClickHouse 뷰. Grafana는 테이블이 아니라 뷰만 조회한다 |
| 일·시간 단위 이력, 분석 | B3: dbt 모델 (6단계). 기간 단위 incremental (delete+insert) |
| B1 조회 비용이 문제가 되면 | B4 refreshable MV로 바꾼다 (5단계 부하 실험에서 판단). ClickHouse 26.8에서 쓸 수 있는지 구현 전에 확인한다 |
| 쓰지 않는 것 | A (Spark 상태 집계), B2 (증분 sum MV) |

### 반대 근거 (권장안의 약점)

권장안을 고르면서 아래 약점을 함께 받아들인다.

1. **조회 비용이 데이터와 함께 커진다.** FINAL과 GROUP BY를 Grafana가 새로고침할 때마다 다시 계산한다.
   - 지금 규모(36만 행)에서는 문제가 아니다.
   - 5단계 부하 테스트에서 행 수를 늘리며 뷰 조회 시간을 잰다. 기준을 넘으면 B4로 바꾼다.
   - 조회 범위는 항상 `event_time` 범위로 좁힌다 (minmax 인덱스).
2. **FINAL을 빼먹으면 틀린다.** 누군가 테이블을 직접 조회하면 merge 전 중복이 섞인다 (3단계에서 실측).
   - Grafana와 dbt는 뷰만 읽게 하는 규칙으로 막는다.
3. **늦게 도착한 데이터가 이미 평가한 윈도우를 바꾼다.** Spark 워터마크는 이 문제를 명시적으로 다룬다 (늦은 데이터는 버린다). B1에는 이 장치가 없다.
   - 알림은 "끝난 지 L초 지난 윈도우"만 평가한다 (허용 지연 L, 예: 10초). 집계 기준 시각은 `event_time`으로 둔다.
   - L보다 늦게 온 행은 대시보드에는 반영되지만, 이미 끝난 알림 판단은 바꾸지 않는다.
4. **CLAUDE.md의 "Spark가 집계" 결정이 줄어든다.** Spark의 역할이 "품질 검사 + 추론 + 적재"로 좁아진다.
   - 포트폴리오에서 "Spark 워터마크 집계"를 보여주는 대신, "중복과 재처리에 강한 집계를 어디에 두었는지와 그 근거"를 보여준다.
   - 대신 Spark 쪽 메모리 여유(현재 3.54 / 4 GiB)에는 유리하다. 상태 집계를 넣으면 state store 메모리가 더 든다.

**A안이 더 나은 경우 (지금은 해당 없음):**
- ClickHouse에 원시 행을 저장할 수 없을 만큼 데이터가 많아서, 집계만 저장해야 할 때
- 알림이 ClickHouse를 거치지 않고 Spark에서 바로 나가야 할 때 (예: Kafka 알림 토픽)

## 설계 (승인 후 구현)

- `flows_dedup` 뷰: `flows_raw FINAL`에서 `fault_type = ''` 행만 남긴다. 모든 집계 뷰의 출발점이다.
- `traffic_by_class_10s` / `_1m` 뷰
  - 키: `toStartOfInterval(event_time, …)` × `pred_service_class`(추론 안 한 행은 `'background'` 또는 `'unclassified'`)
  - 값: `uniqExact(flow_id)`, `sum(bidirectional_bytes)`, `sum(bidirectional_packets)`
- `quality_by_window` 뷰: `flows_rejected FINAL`의 사유별 수, `flows_raw FINAL`의 flag 수
- `pipeline_latency_by_window` 뷰: `inserted_at` 윈도우별 E2E 지연 분위수
- 알림 규칙(6단계): 닫힌 윈도우(`window_end ≤ now() − L`)만 평가한다. 기준선 대비 급증 비율로 판단한다.

## 검증 기준 (구현 후)

| 항목 | 기준 |
|---|---|
| 합계 일치 | 모든 윈도우·클래스의 `uniqExact(flow_id)` 합 = `flows_raw` FINAL의 정상 행 수 (예: 364,054). 바이트 합 = 원시 `sum(bidirectional_bytes)` FINAL. 차이 0 |
| 중복 내성 | 장애 테스트(배치 1개 이중 기록) 직후 OPTIMIZE 전에 계산한 집계 = 깨끗한 실행의 집계. 모든 (윈도우, 클래스)에서 차이 0 |
| 재추론 반영 | ADR 0005 시나리오 ② 직후 클래스별 합계 = 새 모델 예측 분포. 차이 0 |
| 조회 시간 | 1분 윈도우 × 전체 기간 뷰 조회 p95를 5단계에서 측정해 기록한다 (B4 전환 판단 근거) |
| 알림 지연 | 6단계 이상 주입 실험에서 측정한다 (목표안: p95 ≤ 30초, 실측 후 확정) |
