# 모델 정확도 보완 실험 (7단계, 2026-11-11)

- 질문: 플로우 단위 정확도가 70%대다. 이 분류 결과를 믿고 쓸 수 있는가? 확률을 쓰는 방식만 바꿔서 나아지는가?
- 도구: `src/model/eval_improvements.py` (약 1분). 결과 원본: `data/model_eval/holdout_runs.csv`, `session_cv_runs.csv` (git 제외)
- 모델·피처·하이퍼파라미터는 바꾸지 않았다 (`train_baseline.make_model`, 피처 49개). 데이터는 정렬한 `flows_labeled.parquet`이다 (reproduce.md 2절).

## 1. 무엇을 비교했나

같은 확률 출력에 네 가지 판정 방식을 적용했다.

| 방식 | 내용 | 운영에서의 의미 |
|---|---|---|
| A. 기본 | 가장 높은 확률의 클래스 | 지금 Spark가 하는 방식 |
| B. 확신도 임계값 | 최대 확률이 t 미만이면 `unknown` | 모를 때는 모른다고 한다. 답한 비율(coverage)과 답한 것의 정확도를 함께 본다 |
| C. 짧은 플로우 제외 | 패킷 3개 이하는 `unknown` | baseline에서 정확도가 가장 낮던 구간을 뺀다 |
| D. 연결 단위 투표 | 같은 IP 쌍(방향 무시) × 시간 구간(60초 / 300초)의 확률을 평균해 같은 클래스로 판정 | 한 연결 상대와 주고받는 플로우는 같은 서비스일 가능성이 높다 |

- **D의 누수 점검:** IP는 피처가 아니라 묶는 키로만 쓴다. PCAP 파일 이름은 실시간에 알 수 없으므로 쓰지 않았다. 묶을 때는 평가 세션의 노이즈 의심 행까지 넣고(실제로는 라벨을 모른다), 채점은 clean 행에서만 했다.

평가는 두 가지로 했다.
- **held-out:** 운영 분할(세션 17개, clean 1,103행)이다. 학습 시드 10개로 돌려 평균과 범위를 냈다.
  - 시드를 바꾸는 이유가 있다. 행 순서·샘플링만으로 정확도가 흔들리기 때문이다(reproduce.md 2절). 한 번의 값으로는 비교할 수 없다.
- **session CV:** 전체 clean 5,361행을 세션 단위 5-fold로 나눴고, 분할 시드는 3개다. 평가 세션이 더 다양해서 더 보수적이다.

## 3. 해석

**① 트래픽 양 기준으로는 이미 거의 정확하다.**
- 플로우 개수로 세면 정확도가 72%(held-out), 65%(CV)다. 하지만 바이트로 세면 99.5%, 98.6%다.
- 틀리는 플로우는 대부분 작은 제어·보조 플로우다. 대시보드가 보여 주는 "서비스 유형별 트래픽 양"은 오분류의 영향을 거의 받지 않는다.

**② 확신도 임계값이 가장 효과가 크다.**
- 임계값 0.9를 쓰면 플로우의 62%에만 답한다. 대신 답한 것의 86%가 맞고, 이 플로우들이 트래픽 바이트의 94%를 차지한다.
- 이것이 "정확히 맞춰야 쓸 이유가 있다"는 요구에 대한 현실적인 답이다. 모델이 답을 낸 경우는 믿을 수 있고, 모르는 경우는 `unknown`으로 드러난다.
- 운영자는 임계값으로 "얼마나 답할지"와 "얼마나 정확할지"를 고른다.
- CV에서도 같은 경향이다. 0.65 → 0.81이고, 바이트 87%에 답한다.

**③ 짧은 플로우 제외와 연결 투표는 효과가 작다.**
- 짧은 플로우 제외(C)는 정확도를 +0.01–0.04 올린다. 확신도 임계값이 같은 플로우를 이미 대부분 거르므로 따로 둘 이유가 약하다.
- 연결 투표(D)는 정확도를 +0.02 올리지만, **바이트 정확도를 떨어뜨린다**(CV 0.986 → 0.946).
  - 한 연결 안에서 큰 플로우가 맞게 분류돼도, 같은 그룹의 많은 작은 플로우가 투표에서 이기면 큰 플로우까지 틀린 클래스로 바뀐다.
  - 바이트로 가중해서 투표하면 나아질 수 있다. 다만 효과가 작은 방식이라 더 파지 않는다.

**④ 판정 방식만으로는 "모든 플로우 90%"에 갈 수 없다.**
- 전부 답할 때의 상한은 이 피처로 약 0.72–0.75다. 이 값을 올리려면 판정 방식이 아니라 **입력 정보**를 늘려야 한다.
- 오류가 몰린 곳(baseline 혼동 행렬)은 두 군데다.
  - email: 학습 세션이 2개뿐이라 대부분 voip로 틀린다.
  - chat ↔ voip: 작은 플로우의 통계가 비슷하다.
- 후보:
  1. **앞쪽 N개 패킷의 크기·방향·간격 시퀀스**: NFStream `splt_analysis`로 새 라이브러리 없이 뽑을 수 있다. 지금 피처는 평균·최소·최대 같은 요약 통계뿐이다. 패킷 순서 정보는 암호화 트래픽 분류에서 널리 쓰는 신호다. 추출과 메시지 스키마가 바뀌므로 승인 후 진행한다.
  2. VPN-PCAPs를 추가해 세션 수를 늘린다. 특히 email이 부족하다.
  3. 하이퍼파라미터·클래스 가중치 탐색: 시드 흔들림(±0.005–0.02)보다 큰 개선만 인정한다.

**⑤ 운영 모델 A의 0.746은 높게 나온 경우다.**
- 같은 설정의 시드 10개 평균은 0.723이고 범위는 0.719–0.729다.
- 발표에서는 "held-out 정확도 약 0.72, 학습 순서·시드에 따라 ±0.02"로 말하는 것이 정직하다. 문서에 있는 A의 값 0.746은 그 모델 하나의 실측으로 남긴다.

## 4. 다음 할 일 (제안)

- **파이프라인 적용 (B):** Spark 추론에 확신도 임계값을 넣어 낮은 확신도는 `unknown`으로 적재한다. 대시보드에는 "답한 비율 / 답한 것의 정확도"를 보이고 급증 알림은 확신 예측만 센다. 임계값은 설정값으로 둔다(기본 0.8 제안).
  - 영향: `traffic_class`에 `unknown`이 추가된다. 집계 뷰, dbt accepted_values, held-out 정확도 뷰를 손봐야 한다.
- **피처 확장 실험 (④-1):** 오프라인에서 먼저 잰다. 시드 범위를 넘어 개선될 때만 파이프라인에 반영한다.
