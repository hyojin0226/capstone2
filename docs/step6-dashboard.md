## 1. 집계 뷰 (2026-11-10)

`infra/clickhouse/schema/007_aggregation_views.sql` (ADR 0004 설계, ADR 0007 결정 3)

| 뷰 | 내용 |
|---|---|
| `flows_dedup` | `flows_raw FINAL`에서 오류 주입 행 제외. `traffic_class` = 추론함 → 예측 클래스 / F2 배경 → `background` / F2 통과·soft 품질 실패 → `unclassified` (모든 행이 정확히 한 클래스) |
| `traffic_by_class_10s`, `_1m` | `event_time` 윈도우 × `traffic_class` → 플로우 수, 바이트, 패킷 |
| `quality_by_window` | 송신 시각 10초 윈도우의 `rejected:<사유>`, `flagged`, `injected` (긴 형식) |
| `pipeline_latency_by_window` | 적재 시각 10초 윈도우의 E2E p50/p95/p99 |
| `pipeline_batches_dedup` | 배치 지표. `is_reprocess`로 재처리 배치 구분 |

- 플로우 수는 `uniqExact(flow_id)` 대신 `count()`로 센다. `flows_dedup`이 FINAL이라 flow_id당 한 행이고, 아래 합계 검증으로 확인했다.
- 품질 뷰의 윈도우는 송신 시각(Kafka 타임스탬프)이다. 거부 행은 파싱이 안 돼 `event_time`이 없을 수 있다.
- 지연 뷰는 FINAL의 마지막 쓰기를 기준으로 한다. 장애로 다시 쓴 행은 다시 쓴 시각 기준 지연이 된다 (그래서 중복 내성 비교에서는 뺀다).

### 1-1. 검증 (`infra/scripts/verify_views.py`, ADR 0004 검증 기준)

| 검증 | 방법 | 결과 |
|---|---|---|
| 1. 합계 일치 | 뷰의 모든 윈도우·클래스 합 = `flows_raw FINAL` 정상 행 = replay가 보낸 정상 메시지 수. 거부 사유별·flag·주입 수 = 원천 | **통과** (4번 측정 모두). 플로우 364,054, 바이트 20,097,582,203, 패킷 21,389,554. 거부 903 / 449 / 438, 주입 3,701 |
| 2. 중복 내성 | 오류 1% 장애 테스트(쓰기 도중 SIGKILL) 직후, **OPTIMIZE 전**에 뷰 스냅샷을 찍는다 (`failure_test.sh`의 새 `PRE_OPTIMIZE_HOOK`). OPTIMIZE 뒤 다시 비교 | **통과.** 스냅샷 시점에 `flows_raw`에 merge 안 된 중복 189행이 있었다 (FINAL 없이 세면 364,243). 트래픽 72칸, 품질 65칸 모두 OPTIMIZE 전후 같다 |
| 3. 재추론 반영 | 시나리오 ② A → B 뒤: 추론 행이 모두 B이고, 뷰의 클래스별 합 = `flow_predictions`의 B 예측 분포. B → A로 되돌린 뒤 같은 검사 | **통과.** B: chat 985, email 670, file_transfer 1,034, streaming 2,000, voip 4,069. A로 복구: 1,009 / 652 / 1,030 / 2,010 / 4,057. 운영 모델은 A로 돌려놓았다 |

### 1-2. 검증 중 발견: `verify_step3` 배치 합계 검사

- 시나리오 ②를 스트리밍 적재 직후(`archive_test.sh` 다음)에 돌리자 `verify_step3`의 "pipeline_batches 합계 = 테이블 수" 검사가 실패했다. 배치 합이 정확히 두 배였다.
- 원인: 스트리밍 배치(`batch_id` < 1,000,000)와 재처리 배치(≥ 1,000,000)는 같은 데이터를 각각 한 번씩 처리한 기록이다. 검사가 둘을 합쳤다.
  - 4단계에서는 시나리오 ②를 시나리오 ① 뒤에 돌렸다. 시나리오 ①이 배치 테이블을 비우므로 그룹이 하나뿐이라 드러나지 않았다.
  - 파이프라인 문제가 아니라 검사의 가정 문제다.
- 수정: 그룹마다 따로 테이블과 맞춘다. 지금 상태(스트리밍 + 재처리 A→B→A)에서 두 그룹 모두 일치하고, **15/15 통과**다.

- `grafana_ro` 권한 확인: SELECT는 되고, `CREATE TABLE`·`INSERT`는 권한 오류(497), `max_memory_usage` 5 GB 요청은 상한 오류(452), `SET readonly = 0`은 거부(164).

- 값 일치 검사는 **적재가 멈춘 상태에서** 돌려야 한다. replay 도중에 돌리면 Grafana 경유 조회와 직접 조회 사이에 행이 늘어 4건이 어긋났다(실제 불일치가 아니라 측정 시점 차이). replay가 끝난 뒤 20/20.

### 2-3. 발견: 플러그인이 보내는 `max_execution_time`

- 처음 설정(`queryTimeout: 30`)에서는 모든 패널이 `Setting max_execution_time shouldn't be greater than 30`(452)로 실패했다.
- 원인: 플러그인은 데이터소스의 `queryTimeout`에 **4초를 더한 값**을 쿼리 설정으로 보낸다. `getSetting('max_execution_time')`로 재 보니 `queryTimeout` 20 → 24였다. 30이면 34가 되어 `grafana_ro` 상한 30초를 넘는다.
- 조치: 상한(서버 쪽 보호)은 그대로 두고 `queryTimeout`을 20초로 낮췄다. 상한이 제 역할을 한다는 것이 이 오류로 확인되었다.
- `readonly = 1`이 아니라 2인 이유도 같다. 플러그인이 쿼리마다 설정을 보내므로 설정 변경 자체를 막으면 모든 쿼리가 실패한다. 대신 상한으로 범위를 묶었다.

## 3. 패널 조회 비용 (ADR 0007 결정 4, 2026-11-10)

### 3-1. 방법 (`infra/scripts/panel_cost.py`)

- 5단계 `query_cost.py`는 집계 쿼리 하나만 쟀다. 이번에는 **대시보드 파일의 패널 쿼리 12개 전부**를 Grafana와 같은 사용자 `grafana_ro`로 잰다.
- 시험 DB `capstone_pcost`에 `flows_raw`·`flows_rejected`·`pipeline_batches`를 같은 DDL로 만들고 007 뷰를 그 DB를 보도록 다시 만든다. 운영 DB는 건드리지 않는다.
- 원천 행(66만 행, 오류 주입 포함)을 복사한다. 복사본마다 `flow_id`를 새로 만들고, 시각 열을 "초당 10,000건이 끊김 없이 들어와 지금 끝난 테이블"이 되도록 다시 매긴다. 적재 시각은 송신 + 6초로 둔다.
- 패널 범위는 Grafana 기본값인 최근 15분이다. `$__timeFilter`는 플러그인과 같은 식으로 바꾼다.
- 두 가지를 잰다:
  - 패널별: 하나씩 7회 → p50/p95, 읽은 행, 메모리, CPU
  - 새로고침: 12개를 동시에 7회 (Grafana가 새로고침 때 하는 일) → 완료 시간, 새로고침 1회의 ClickHouse CPU 초. 10초 새로고침 기준 CPU 점유율 = CPU 초 / 10초 / 12코어
- 두 상태를 잰다: insert 직후(part 10–15개, 스트리밍 중과 비슷) / `OPTIMIZE FINAL` 뒤(part 1개). 측정 중에는 Spark를 멈췄다.
- 기준 (ADR 0007 결정 4): 패널 p95 ≤ 1초, 10초 새로고침에서 CPU ≤ 50%.

### 3-2. 결과

| `flows_raw` 행 (10,000/s 기준 기간) | 가장 느린 패널 p95 (insert 직후 / merge 후) | 새로고침 p50 (직후 / 후) | CPU, 10초 새로고침 (직후 / 후) | 기준 |
|---|---|---|---|---|
| 330만 (6분) | 0.35 / 0.21초 | 0.68 / 0.41초 | 6% / 4% | **통과** |
| 1,800만 (30분) | 1.87 / 0.81초 | 3.3 / 1.4초 | 28% / 13% | 직후 p95 초과 |
| 3,600만 (60분) | 3.62 / 1.22초 | 6.5 / 2.2초 | 52% / 20% | 직후 둘 다 초과 |
| 7,200만 (120분) | 20.9 / 5.7초 | **10.4** / 4.1초 | **85%** / 38% | 새로고침이 10초 간격을 넘는다 |

- 9개 패널이 `flows_raw FINAL` 전체를 읽는다(읽은 행 = 테이블 행 수). 범위가 최근 15분이어도 그렇다. 5단계 11-1과 같은 원인이다(정렬 키가 해시값 `flow_id`).
- 그래서 비용이 테이블 크기에 비례한다. 새로고침 1회의 CPU는 insert 직후 약 1.4초/백만 행, merge 후 약 0.6초/백만 행이다.
- 작은 패널(거부 수, 배치 지표)은 3–30 ms다. held-out 정확도 패널(작은 표)은 약 0.11초로 크기와 무관하다.
- 메모리는 패널당 최대 134 MiB로, `grafana_ro` 상한 1 GB에 한참 못 미친다. 측정 중 실패한 쿼리는 0건이다.

### 3-3. 바로 고친 것: 품질 뷰가 `flows_raw`를 두 번 읽었다

- `quality_by_window`가 flag 수와 오류 주입 수를 따로 세느라 `flows_raw FINAL`을 두 번 스캔했다. 그래서 가장 비싼 패널이었다 (72M 행 직후 p95 20.8초, 읽은 행 1.45억).
- 한 번의 스캔에서 둘 다 세고 `ARRAY JOIN`으로 긴 형식을 만들도록 고쳤다. 출력은 바이트 단위로 같고(md5 일치), `verify_views.py` `compare`와 `sums` 모두 통과했다.
- 효과 (3,600만 행 재측정): 이 패널의 p95가 3.62 → **1.84초**(insert 직후), 1.12 → **0.47초**(merge 후)로 줄었다. 새로고침 p50은 6.5 → 5.6초(직후)다. 새로고침 CPU 합계는 54% / 21%로 거의 같다. part 수에 따라 흔들리는 범위 안이다.

### 3-4. 결정: TTL은 적용하지 않는다 (2026-11-10 사용자 승인)

ADR 0007 결정 4는 "기준을 넘으면 TTL"이었다. 측정해 보니 이 프로젝트의 사용 방식에서는 TTL이 맞는 도구가 아니다.

1. **기준을 지키려면 TTL이 매우 짧아야 한다.**
   - 기준(insert 직후 패널 p95 ≤ 1초)을 지키는 크기는 약 1,500만 행이다.
   - 10,000 msg/s라면 TTL이 약 25분이어야 한다. 처음 예로 든 24시간은 10,000/s에서 8.6억 행이라 아무 효과가 없다.
2. **25분 TTL은 검증 절차를 깨뜨린다.**
   - `verify_step3`, `verify_views sums`, 재처리 시나리오 ①②의 전후 비교는 실행 전체의 행을 원천과 맞춘다.
   - dbt 시간 단위 이력도 행이 지워지기 전에 만들어야 한다.
   - 이 프로젝트의 핵심 성과인 "합계가 맞는다"를 보이는 데 필요한 행을 대시보드 속도를 위해 지우게 된다.
3. **이 정렬 키에서는 TTL 자체도 비싸다.**
   - ClickHouse TTL은 merge 때 행을 지운다. 정렬 키가 해시값이라 merge된 part 하나에 모든 시간대가 섞여 있다.
   - 그래서 통째로 버릴 part(`ttl_only_drop_parts`)가 없다. 만료 행을 지울 때마다 큰 part 전체를 다시 쓴다.
   - 또한 기본 `merge_with_ttl_timeout`이 4시간이라, 짧은 TTL은 따로 튜닝해야 실제로 지워진다.
4. **실험은 실행마다 테이블을 초기화한다.** 계획된 6단계 측정 대부분이 기준 안에 들어간다.
   - 이상 주입: 실행당 수 분이다.
   - 오탐 측정 30분: 10,000/s면 1,800만 행으로 경계에 걸린다. **5,000/s(900만 행)로 돌리면 기준 안이다.**

**결정 (A안 + 운영 범위 명시):**
- TTL을 적용하지 않는다.
- 10초 새로고침 대시보드의 운영 범위를 **`flows_raw` 약 1,500만 행 이하**로 문서화한다 (10,000/s 약 25분, 5,000/s 약 50분, 2,000/s 약 2시간).
- 이 범위를 넘는 긴 실행은 새로고침을 30초 이상으로 늘린다 (CPU가 3분의 1이 된다).
- 오탐 30분 측정은 5,000 msg/s로 한다.
- 알림 규칙 쿼리도 같은 뷰를 10초마다 읽는다. 그 비용은 다음 단계(알림)에서 함께 잰다.

**TTL(또는 시간순 키)이 맞는 조건 (기록):** 테이블을 초기화하지 않고 계속 운영하는 환경이다. 그때는 5단계 11-3에 기록한 대로 이벤트 시각이 원본에서 고정되어야 한다. 그러면 시간순 정렬 키와 `ttl_only_drop_parts`를 함께 쓸 수 있고, 둘 다 싸게 동작한다.

측정 결과: `data/loadtest/panel_cost_v1.csv`(4개 크기, 고치기 전), `panel_cost.csv`(3,600만 행, 고친 뒤), `*_refresh*.csv`.

## 4. 증폭 주입 · 급증 알림 · 탐지 지연 (ADR 0007 결정 5, 6, 2026-11-10)

### 4-1. 구성

- **주입 도구** (`src/replay/producer.py`):
  - `--amplify CLASS:FACTOR:START:DURATION`: START초부터 DURATION초 동안 라벨이 CLASS인 플로우를 FACTOR배로 보낸다.
  - 증폭분은 새 `flow_id`(`run_flow_id(..., "<run_id>-amp", 회차)`)와 `run_id` `<run_id>-amp`로 보낸다.
  - 계획(`amplify_plan`)과 실제 추가 송신 수(`amplify ... extra_sent`)를 로그에 남긴다.
- **알림 규칙** (`grafana/provisioning/alerting/traffic_spike.yaml`):
  - 마지막 닫힌 10초 윈도우(`now − 15초` 기준, L = 15초)의 클래스별 플로우 수를 직전 5분(30개 윈도우) 평균으로 나눈다.
  - 비율 > K = 3이고, 윈도우 플로우 ≥ 20, 기준 윈도우 ≥ 24개일 때 알린다.
  - 평가 주기는 10초, pending은 0초다. 분류된 클래스만 본다(background, unclassified 제외).
- **측정 하네스** (`infra/scripts/alert_test.sh`, `alert_summary.py`):
  - 초기화 → 섞은 배경 트래픽 + 증폭 구간 5개 → 따라잡기 → 요약.
  - 구간은 330초부터 330초 간격이고, 각 구간은 30초다. 간격 330초 = 기준선 5분 + 주입 30초라서, 다음 구간의 기준선에 앞 구간이 섞이지 않는다.
  - 탐지 = 같은 클래스의 Alerting 전이가 [구간 시작, 끝 + 120초] 안에 있는 것이다.
  - 지연 = 주입 시작부터 그 전이까지다. Grafana 상태 이력 API `/api/v1/rules/history`에서 읽는다.

### 4-2. 측정 전에 고친 것 두 가지

**① 배경 트래픽을 섞는다 (`--shuffle`)**
- 데이터셋 타임라인 순서로 보내면 분류되는 플로우가 매 회차 앞쪽에 몰린다.
- 그래서 일정 속도 모드에서는 회차가 바뀔 때마다 주입하지 않아도 "급증"이 생긴다. 이 상태로는 오탐과 탐지를 구분할 수 없다.
- `--shuffle`은 회차마다 행 순서를 섞는다(시드 고정 7). 그러면 클래스 구성이 일정한 배경 트래픽이 된다.

**② 증폭 구간은 wall clock으로 잰다**
- 처음에는 증폭 구간을 `time.monotonic()` 경과 시간으로 정했다.
- 그런데 실측해 보니 적재 시각 기준으로 구간이 3초 늦게 시작했고, 길이도 30초가 아니라 약 33초였다.
- 원인은 WSL의 시계다. 부하가 걸리면 wall clock이 monotonic보다 약 9.5% 빨리 간다(monotonic 60초 = wall 65.7–65.9초). 유휴 상태에서는 차이가 없다.
- 탐지 지연은 wall clock(`replay_sent_ms`, Grafana 이력 시각)으로 재므로, 구간도 wall clock(`time.time()`)으로 정하도록 바꿨다. 이후 계획과 실제 구간의 차이는 16–55 ms다.
- 기록: 이 환경에서 monotonic 기반 경과 시간과 epoch 시각을 섞어 계산하면 부하 중 약 10% 오차가 난다.

### 4-4. 해석

**① 예측 클래스는 주입한 배율만큼 늘지 않는다 (×2 대신 ×8을 잰 이유)**
- 증폭은 라벨 기준으로 한다. 그런데 알림이 보는 값은 예측 클래스다.
- 라벨이 streaming인 증폭 행의 약 44%는 F2 필터에서 background가 된다. 나머지 일부도 다른 클래스로 오분류된다.
- 그래서 예측 비율은 라벨 비율의 0.66–0.72배다. 대략 예측 비율 ≈ 1 + 0.56 × (배율 − 1)이다.
- 이 관계에서 배율 ×2(예측 비율 약 1.6)는 K = 3에 닿을 수 없다. 그래서 ADR의 {2, 3, 5} 대신 {3, 5, 8}을 쟀다.
- 결과도 이 예측과 맞는다. ×3(예측 2.0–2.5)은 0/10, ×5(2.9–3.7)는 9/10, ×8(4.3–4.9)은 10/10이다.
- 놓친 1건(10,000/s ×5 구간 2)은 예측 비율 최대가 2.93으로, 임계값 바로 아래였다.
- 정리하면 이 규칙의 실제 감도는 "라벨 기준 약 5배 이상"이다. 감도를 정하는 것은 임계값 K보다 모델의 F2·분류 단계다.

**② 지연이 10초 단위로 묶이는 이유와 구성**
- 같은 실행 안에서는 지연이 27.8/37.8/47.8초처럼 10초 간격으로만 다르다.
- 이유는 구간 시작이 송신 시작으로부터 330초의 배수라는 점이다. 그래서 모든 구간이 윈도우 경계와 평가 시각에 대해 같은 위상에 있다.
- 지연의 차이는 몇 번째 닫힌 윈도우에서 비율이 K를 넘었는가뿐이다. 주입이 윈도우 중간에 시작하면 첫 윈도우는 일부만 증폭되어 K를 못 넘을 수 있다.
- 구성을 나누면 다음과 같다.
  - 첫 완전한 윈도우가 닫히기까지 0–10초(첫 윈도우가 부분이면 +10초)
  - L 15초
  - 평가 위상 0–10초
  - 조회 0.1–1.4초
- 이를 더하면 25–47초로, 실측 범위와 맞는다. ADR의 예상 20–35초는 "첫 윈도우가 부분일 때 다음 윈도우를 기다리는 10초"를 빼먹은 것이다.

**③ refire: pending 0초 + 30초 구간**
- 증폭 30초는 10초 윈도우 3개에 걸친다.
- 중간 평가에서 비율이 K 아래로 떨어지면 Normal로 돌아갔다가 다음 윈도우에서 다시 Alerting이 된다. 원인은 부분 윈도우, 또는 기준선에 앞 윈도우가 섞이는 것이다.
- 운영에서는 같은 사건에 알림이 두 번 가는 것이다. Grafana 규칙의 `keep_firing_for`(예: 30초)를 쓰면 한 번으로 묶을 수 있다. 탐지 지연에는 영향이 없다.

**④ 조정 후보 (이번에는 바꾸지 않는다)**
- 30분 정상 트래픽에서 오탐이 0건이라 감도를 올릴 여유는 있어 보인다.
- 다만 섞은 replay는 실제 트래픽보다 훨씬 고르다. 기준선 105/10초에서 포아송 흔들림은 약 ±10%다. 그래서 오탐 0건이 실제 환경의 여유를 보장하지 않는다.

| 조정 | 기대 효과 | 대가 |
|---|---|---|
| L 15 → 10초 | 지연 −5초 | 5,000/s E2E p95가 8–14초라, 부하가 몰리면 닫히지 않은 윈도우를 평가한다 (늦은 행 → 탐지 누락) |
| 윈도우 10 → 5초 | 지연 약 −5–10초 (부분 윈도우 대기 감소) | 2,000/s에서 윈도우당 약 50건이라 흔들림이 커진다. 최소량 20건 조건이 더 자주 걸린다 |
| K 3 → 2.5 | ×5 탐지가 안정적이다(10,000/s 2.93 누락 해소). ×3은 여전히 대부분 못 잡는다 | 실제 트래픽에서 오탐이 늘 수 있다 |
| `keep_firing_for` 30초 | refire 제거 | 알림 해제가 30초 늦어진다 |

- p95 ≤ 30초 목표에 가장 크게 걸리는 것은 구조적 지연이다(닫힌 윈도우 + L + 평가 주기). 임계값 K는 이 지연을 줄이지 못한다.
- 목표를 지키려면 윈도우·L을 함께 줄이고, 그만큼 늦은 행 허용을 포기해야 한다. 이 트레이드오프를 기록으로 남기고 현재 설정(10초 / L 15초 / K 3)을 유지한다.

## 5. Kafka lag 패널 (ADR 0007 결정 7, 2026-11-10)

### 5-1. 왜 따로 기록해야 하나

- **lag**은 Kafka에 쌓였지만 아직 처리되지 않은 메시지 수다(파티션 끝 offset − 처리한 offset). 계속 늘면 파이프라인이 유입을 못 따라가고 있다는 뜻이다.
- 보통은 `kafka-consumer-groups`로 소비자 그룹의 lag을 본다. 하지만 Spark Structured Streaming은 처리 위치를 Kafka 그룹이 아니라 **자기 체크포인트**에 저장한다. 그래서 Kafka 쪽에서는 lag이 보이지 않는다.
- 그래서 Spark가 배치를 끝낼 때 남기는 `pipeline_batches.end_offsets`(파티션별 마지막 offset + 1)를 처리 위치로 쓴다.
  - 이 행은 flows_raw·flows_rejected 쓰기가 끝난 **뒤에** 쓰인다.
  - 따라서 여기서 말하는 lag은 "ClickHouse 적재까지 끝나지 않은 메시지 수"다.

### 5-2. 구성 (새 라이브러리·서비스 없음)

- **`infra/clickhouse/schema/009_pipeline_lag.sql`**
  - `pipeline_lag(ts, topic, partition, end_offset, processed_offset, lag, last_batch_age_s)`, MergeTree.
  - 쓰는 프로세스가 하나이고 추가만 하므로 중복 정리가 필요 없다. 그래서 대시보드가 테이블을 직접 읽는다.
  - `reset_pipeline.sh`가 이 테이블도 비운다.
- **`infra/scripts/lag_reporter.py`** (venv에서 실행, 5초 주기)
  - confluent-kafka로 파티션별 high watermark를 읽는다. 소비자 그룹에는 가입하지 않는다.
  - ClickHouse에서 스트리밍 배치(`batch_id < 1,000,000`)의 파티션별 `end_offsets` 최댓값을 읽는다.
  - 둘의 차이를 파티션별 한 행으로 쓴다. 브로커나 ClickHouse가 잠깐 없어도 멈추지 않는다.
  - 토픽을 다시 만든 직후에 처리 위치가 끝보다 크면 lag을 0으로 자른다.
- **대시보드 5행 (패널 14개):**
  - "Kafka lag: 처리 안 된 메시지 (파티션별)": 쌓은 막대가 아니라 쌓은 선으로 그린다.
  - "마지막 스트리밍 배치 후 경과" (`last_batch_age_s`).
  - reporter가 꺼져 있으면 두 패널은 비어 있다.

- 측정 원본: `data/loadtest/lag_test.csv`, `data/loadtest/lag-r5000-*_series.csv`(5초 시계열).

### 5-4. 해석

- 이 패널로 "Spark가 멈췄다"(배치 후 경과가 계속 늘어난다)와 "Spark는 돌지만 느리다"(경과는 짧은데 lag이 계속 는다)를 구분할 수 있다.
  - 4절 알림 규칙은 트래픽 급증만 본다.
  - 파이프라인 정체 알림(예: lag > 정상 최대의 2배가 1분 지속)은 이 테이블 위에 같은 방식으로 만들 수 있다. 이번 범위에서는 패널까지만 둔다.
- 장애 복구 시간 약 53초 중 28초가 Spark 기동이다. 따라잡기는 30초 이내였다.
  - 그래서 복구 시간을 줄이려면 처리 속도를 높이는 것보다 기동 시간을 줄이는 것이 먼저다(예: 모델 로드, 세션 준비).

## 6. dbt (ADR 0007 결정 8, 2026-11-10)

### 6-1. 설치와 구성

- **dbt**는 SQL `SELECT`로 분석 테이블을 정의하는 도구다. 의존 순서대로 만들고(`ref`), 테스트하고, 문서를 만든다.
  - 결과 테이블을 만들어 두면 원천이 reset되거나 커져도 시간 단위 이력을 싸게 볼 수 있다.
- **설치:** 파이프라인 venv와 섞이지 않게 별도 venv `.venv-dbt`를 쓴다.
  - `pip install dbt-clickhouse==1.10.3`이 dbt-core **1.12.6**, dbt-adapters 1.24.5(`< 1.25` 조건 충족)로 해결됐다.
  - 전체를 `dbt/requirements.txt`에 고정했다.
  - 실행하면 "dbt v2가 나왔다"는 안내가 나온다. dbt-clickhouse 1.10.3은 dbt Core v1용이라 v1을 유지한다.
- **연결** (`dbt/profiles.yml`): ClickHouse HTTP 8123, `capstone` 사용자(로컬 테스트 비밀번호, 환경 변수로 덮어쓴다).
  - 결과는 별도 데이터베이스 **`capstone_dbt`**에 둔다. 원천(`capstone`)과 섞이지 않는다.
  - `grafana_ro`는 테이블을 만들 수 없어서 dbt에는 쓰지 않는다.
- **원천** (`models/sources.yml`): 007 집계 뷰 `flows_dedup`, `quality_by_window`와 006 `holdout_eval_rows`다. 대시보드와 같은 원칙이다(테이블 직접 조회 금지).

| 모델 | 구체화 | 내용 |
|---|---|---|
| `stg_flows` | view | `flows_dedup` + `hour` |
| `traffic_hourly` | incremental, `insert_overwrite`, 파티션 = hour | 시간 × 예측 클래스: flows, bytes, packets, runs |
| `quality_hourly` | incremental, `insert_overwrite`, 파티션 = hour | 시간 × 품질 지표 (rejected:<사유>, flagged, injected) |
| `model_accuracy_daily` | table (매번 전체) | 일 × 모델 × 실제 클래스: support, correct, recall |

- **증분 방식 (`insert_overwrite`):**
  - 새로 계산한 시간 파티션을 **통째로 교체**한다(ClickHouse `REPLACE PARTITION`).
  - 같은 시간을 다시 만들어도 행이 덧붙지 않는다. 그래서 재처리 뒤 재빌드가 멱등이다.
  - ADR의 "시간 단위 delete+insert"를 이 전략으로 구현했다. delete+insert는 키가 일치하는 행만 지운다. 그래서 재추론 뒤 어떤 클래스가 그 시간에서 사라지면 옛 행이 남는다.
- **다시 만들 범위** (`macros/hour_filter.sql`):
  - 기본은 대상 테이블의 마지막 시간부터다(그 시간에 늦게 온 행을 반영).
  - 재처리 뒤에는 `--vars '{"start": ..., "end": ...}'`로 범위를 준다(UTC, [start, end)).
- **`model_accuracy_daily`를 증분으로 하지 않는 이유:** 재추론하면 과거 날짜의 값이 바뀐다. 표가 작아서(일 × 모델 × 5클래스) 매번 전체를 만드는 편이 단순하고 맞다.
- **한계 (기록):**
  - 재처리로 어떤 시간의 원천 행이 **모두** 사라지면, 그 시간 파티션은 새 결과에 없어서 교체되지 않는다(옛 값이 남는다).
  - 같은 시간대의 실험을 reset 후 다시 돌리고 재빌드하면, 그 시간은 새 실행의 값으로 바뀐다. 이력은 "현재 원천에서 다시 만든 값"이다.

### 6-2. 테스트 (14개)

- 기본 테스트:
  - not_null: hour, traffic_class, flows, metric, day, model_version, service_class
  - accepted_values: `traffic_hourly.traffic_class`(5클래스 + background + unclassified), `model_accuracy_daily.service_class`(5클래스)
- 직접 만든 테스트 (`dbt/tests/`):
  - `assert_traffic_hourly_matches_source`: 원천에 있는 시간마다 클래스별 `traffic_hourly` 합 = `flows_dedup` 행 수
  - `assert_quality_hourly_matches_source`: 지표별 `quality_hourly` 합 = `quality_by_window` 합
  - `assert_hourly_keys_unique`: 시간 × 키 한 행. 파티션 교체가 덧붙이기로 바뀌면 걸린다
  - `assert_accuracy_consistent`: correct ≤ support, support 합 = `holdout_eval_rows` 행 수
- **테스트가 실제로 잡는지 확인 (일부러 망가뜨리기):**
  - `traffic_hourly`의 chat 행과 `quality_hourly`의 injected 행을 한 번 더 넣었다. 그러자 키 유일성과 합계 일치 테스트가 실패했다. 그 뒤 기간 재빌드로 18/18로 복구했다.
  - 처음 쓴 합계 테스트는 dbt 쪽을 행 단위로 join해서, 같은 행이 두 번 들어가도 행마다 값이 같아 통과했다. dbt 쪽도 키별로 합친 뒤 비교하도록 고쳤다.
  - 값이 0인 지표(`flagged`)는 두 번 들어가도 합이 같다. 이 경우는 유일성 테스트가 잡는다.
